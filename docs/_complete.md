# 🚀 プロジェクト概要：C言語駆動型ポートフォリオサイト

## 1. コンセプト

* **一言でいうと:** C言語を専用ジェネレーターとして構築する、JavaScript不使用のポートフォリオサイト。
* **解決したい課題:** 大学2年生を迎えるにあたり、これまでの開発・学習の軌跡を集約する場を設けること。同時に、最も得意かつ嗜好する「C言語」をあえてWebのフロントエンド領域（静的生成）に適用することで、独自性のある自己表現を行う。
* **ターゲット:** 自分自身の備忘録として。また、自身の技術力（低レイヤー言語での堅牢な実装力・Web標準技術の応用力・自動化スキルの複合）をアピールしたい技術者や採用担当者。

## 2. 技術スタック

| 領域 | 採用技術 | 備考 |
| --- | --- | --- |
| **フロントエンド（生成）** | **C言語** | WebAssembly等へのコンパイルは行わず、CプログラムをローカルまたはCI上で実行し、静的HTMLを直接出力する自作SSG（Static Site Generator）方式。`snprintf`を用いた厳格なバッファ管理を行う。 |
| **フロントエンド（動的UI）** | **CSS** | JavaScriptは一切使用しない。`:checked`疑似クラスや`:has()`疑似クラスなどのCSS機能を駆使し、状態管理と動的UI表現（アコーディオン、フィルタリング等）を単独で実現する。 |
| **デプロイ・自動化** | **GitHub Actions / Pages** | ソースコードのPushをトリガーとし、「Cソースのコンパイル → Cプログラムの実行（HTML生成） → GitHub Pagesへの自動公開」という一連のCI/CDパイプラインを構築する。 |

## 3. 機能一覧

### MVP（C言語による静的HTML生成・初期リリース必須要件）

* **プロフィール表示機能**
* 氏名、所属、タグライン、バイオグラフィの表示。
* 各種外部アカウント（GitHub、X等）へのリンク集。


* **スキル・ステータス表示機能**
* 主要な技術スタックのテキストサマリー。
* Gittyプロフィール等の外部連携リンクカード。


* **キャリア（経歴・学習歴）タイムライン**
* 時系列に基づいた学習歴やイベント参加歴のリスト生成。


* **実績・プロジェクト一覧表示**
* 各プロジェクトのタイトル、URL、制作時期、カテゴリの表示。


* **C言語コアロジックによる堅牢なデータ処理と出力**
* データを管理・保持する構造体（`struct`）の定義と、内部処理用の一意なID付与ロジックの実装。
* HTML特殊文字（`<`, `>`, `&` 等）のサニタイズ（エスケープ）処理関数の実装。
* 構造体データを安全にHTMLタグへ埋め込み出力するジェネレーター関数の実装。


* **サイトメタ情報・セルフホスト証明**
* 「C言語で生成された」旨の明記。
* C言語のコンパイル時マクロ（`__DATE__`, `__TIME__`）を活用した、最終ビルド日時の自動埋め込み。



### 追加機能（CSSハックを用いた動的UI）

* **インタラクティブ・フィルタリング**
* `<input type="radio">`（`:checked`）と`:has()`を組み合わせた、プロジェクトのカテゴリ別表示・非表示の切り替え。


* **詳細情報のアコーディオン / スライド表示**
* `<input type="checkbox">`（`:checked`）を用いた、実績カードの詳細情報の展開・格納。


* **ホバーアニメーション**
* `:hover`擬似クラスを用いた、リンクカードの浮き上がりやフォーカス演出。



## 4. UI/UX・画面構成（シングルページ構成）

ページ遷移を伴わないSPA（Single Page Application）風の構成を、静的HTMLとCSSのみで実現します。

* **ホーム (`/`):** サイトのトップビュー。氏名、タグライン、および各セクションへのグローバルナビゲーション。
* **プロフィール (`/#about`):** 自己紹介文と外部アカウントのリンク集。
* **スキル (`/#skills`):** Gittyプロフィールへのリンクと主要技術のサマリー。
* **キャリア・実績 (`/#works`):** C言語の構造体から生成された経歴タイムラインと、フィルタリング可能なプロジェクト一覧。
* **フッター:** 「Generated by pure C」のセルフホスト証明と、マクロ生成されたビルド日時の表示。

## 5. ディレクトリ構成ルール

```text
./
├── .github/
│   └── workflows/
│       └── deploy.yml   # CI/CDパイプライン（コンパイル → HTML生成 → Pagesデプロイ）
├── Makefile             # ビルドと生成を自動化するコマンド群 (build, generate, clean等)
├── src/                 # C言語のソースコード（ジェネレーター本体）
│   ├── main.c           # エントリーポイント（全体制御）
│   ├── models.h         # 構造体の定義（データモデル）
│   ├── data.c           # 実際のポートフォリオデータ（配列・構造体初期化）
│   ├── render.h         # レンダリング・サニタイズ関数のプロトタイプ宣言
│   └── render.c         # HTML文字列出力ロジック（サニタイズ処理、snprintf利用）
├── styles/              # CSSファイル群
│   └── main.css         # :checkedや:has()などのロジックとデザインを記述
└── dist/                # 公開用ディレクトリ（最終的なデプロイ先・Git管理外推奨）
    ├── index.html       # Cプログラムにより自動生成された最終HTML
    └── main.css         # styles/ からコピーされたCSS

```

## 6. 実装上の重要な制約・注意点（背景知識と設計方針）

### 6.1. 安全なメモリ・文字列操作とエスケープ処理の徹底

* **背景:** C言語による動的な文字列結合は、バッファオーバーフローを引き起こす致命的なリスクを伴います。また、文字列データをそのままHTMLに出力すると、クロスサイトスクリプティング（XSS）に代表される脆弱性や、意図しないタグの破壊を招きます。
* **方針:** 標準の`sprintf`の利用を禁止し、バッファサイズを厳格に指定できる`snprintf`を徹底して使用します。また、`render.c`内で文字列を出力する際は、必ず独自のHTMLエスケープ関数（`<` を `&lt;` に変換等）を経由させ、Webアプリケーションとしての堅牢性を担保します。

### 6.2. CSSハック成立のための厳密なID整合性の確保

* **背景:** JavaScriptのDOM操作を代替し、CSSの`:checked`と`:has()`のみでUIの状態管理を行う手法では、トリガーとなる`<input>`要素と、それと紐づく`<label>`要素の`id`属性および`for`属性が、1対1で完全に一致している必要があります。
* **方針:** `render.c`におけるC言語のループ処理内で、各データ要素やフィルタリング項目に対して `item-1`, `item-2` といった一意の連番IDを動的かつ規則的に生成し、HTML出力時に正確にバインディング（結合）させます。

### 6.3. 継続的インテグレーション（CI/CD）によるDevOpsの実践

* **背景:** 「生成されたHTML（`dist/index.html`）」を直接Gitでバージョン管理することは、差分（Diff）が肥大化し管理上美しくありません。また、ローカルで毎回手動コンパイル・生成を行う作業はヒューマンエラーの原因となります。
* **方針:** GitHub Actionsを導入し、`data.c`などのCソースコードがPushされた段階で、クラウド環境上で自動的に `make build` と `make generate` を実行します。その後、生成された静的ファイルを直接GitHub Pagesへデプロイする仕組みを構築することで、低レイヤー言語のプロジェクトにモダンなDevOpsサイクルを適応させます。
