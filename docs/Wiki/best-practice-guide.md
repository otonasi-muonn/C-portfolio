# ベストプラクティスガイド（C-portfolio）

このガイドは `C-portfolio` で安全かつ再現性のある開発を行うための実践ルールをまとめたものです。  
`claude-code-best-practice` の考え方（設定階層、Skills運用、検証ループ、コンテキスト管理）を、このリポジトリ向けに最小化して適用しています。

---

## 1. 実装前（設計と範囲の固定）

- `docs/DD.md` と `docs/_complete.md` を先に読み、設計から逸脱しない
- 変更対象ファイルを先に決め、目的外の修正を入れない
- C出力の安全条件（`snprintf`, `html_escape`）を事前確認する

**開始前チェック**

- 何を変えるか（目的）
- どのファイルを変えるか（範囲）
- 何で確認するか（`make all`）

---

## 2. 実装中（差分最小・責務明確）

- 既存責務に従う（`data.c` = データ、`render.c` = HTML組み立て、`main.c` = 制御）
- 1変更1意図の粒度を守り、レビューしやすい差分を維持する
- 文字列処理はバッファ長を意識し、戻り値確認を省略しない

**禁止寄りの項目**

- `sprintf` の使用
- `system`, `popen` の追加
- サイレント失敗（握りつぶし）

---

## 3. 実装後（検証ループ）

最終検証は必ず以下を実行します。

```bash
make all
```

**確認項目**

- ビルドが成功する
- `dist/index.html` が生成される
- `dist/main.css` が配置される
- 変更が意図したファイルに限定されている

---

## 4. Skills / TAKT の使い分け

このリポジトリでは、ECC全量ではなく最小Skillsを使います。

- `tdd-workflow`: 設計確認 -> 実装 -> `make all` の流れを固定
- `security-review`: `snprintf` / `html_escape` / 危険API混入を確認
- `verification-loop`: 仕上げの検証ルーチン
- `strategic-compact`: フェーズ境界でのコンテキスト圧縮判断

TAKTを使う場合は、`plan -> implement -> review` の流れを守り、  
最終判定は常に `make all` を基準にします。

---

## 5. コンテキスト管理（長時間作業向け）

- 調査フェーズ完了後に要点を文書化してから次へ進む
- 実装途中で不要に文脈を切らない
- 別タスクへ切り替える前に必要情報を `docs/` へ残す

目安:

- 調査 -> 実装 に移る時
- 大きな修正を終えた時
- 無関係タスクへ移る時

---

## 6. ドキュメント運用

- 実装や運用ルールを変えたら `docs/Wiki/` も同時更新する
- README から到達できる導線を維持する
- 汎用テンプレート文言ではなく、このリポジトリ固有の説明を書く
